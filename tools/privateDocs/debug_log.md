## U28 故障结论

U28 的各个 Y 输入测得约 1.6 V，但公共输出 Z 为 0 V；重新焊接 U28 后恢复正常。因此这次故障确定在 U28 芯片或其焊接连接，不是 ADC 阈值、扫描映射或 4051 地址建立时间造成的。

从“所有 Y 输入正常但 Z 为 0 V”推断，最可疑的焊点依次为：

1. `Z/COM` 引脚虚焊或其焊盘/走线接触不良；若 0 V 是在 MCU 端测得，这是最符合现象的原因。
2. `VCC` 虚焊，使芯片没有正常供电。
3. `E` 虚焊或没有可靠保持低电平，使 Z 进入高阻态；后级 ADC 输入可能随后表现为接近 0 V。
4. `GND/VEE` 公共焊点虚焊。

地址 A/B/C 某一个虚焊通常只会选错或随机选择 Y 通道。由于所有 Y 输入当时都约为 1.6 V，它不太容易稳定产生“Z 始终为 0 V”，所以优先级低于上述四项。

## 2026-07-19：500 Hz 目标完成

![1784475670239](image/debug_log/1784475670239.png)

最终实测完整 24 通道扫描率达到 **695 Hz**，对应平均扫描周期约为：

`1000 / 695 ≈ 1.44 ms`

已经超过原定 500 Hz 目标约 39%，可满足当前磁轴键盘的采集需求。后续不再单纯以提高空载扫描率为主要目标，应优先验证模拟信号质量、端到端延迟和磁轴算法稳定性。

### 本轮问题与优化过程

1. 初始基线为 83.170 Hz，配置为 `settle-time-us = 500`、`polling-interval-ms = 5`，每通道包含一次 dummy read 和一次有效 ADC read。
2. U28 的 Y 输入均约为 1.6 V，但公共端 Z 始终为 0 V。重新焊接 U28 后恢复，说明根因位于芯片焊接或其供电、使能、公共端连接，而不是扫描映射和 ADC 阈值。
3. 逐步缩短轮询与稳定时间，并取消不必要的 dummy read。
4. 将扫描任务移到独立工作队列，避免连续扫描长期占用 ZMK 系统工作队列。
5. 原实现每帧执行 24 次独立 `adc_read()`。优化后，在每个 4051 地址下一次性采集 U26、U27、U28 三个 SAADC 输入，使每帧 ADC 驱动调用从 24 次减少到 8 次。
6. 上位机曾出现明显历史数据积压，看起来像按键响应延迟。根因不是 USB CDC 带宽不足，而是每帧通过 Qt 信号排队进入 GUI 线程。修改为有界共享队列、批量取帧、积压时丢弃最旧帧，并限制绘图点数后恢复实时显示。
7. `settle-time-us` 从 50 µs降到 30 µs后，扫描率起初变化不明显。检查确认生成设备树中已经是 `0x1e`（30 µs），实际原因是几十微秒延时仍使用 `k_usleep()`，调度和唤醒开销掩盖了参数差异。改用 `k_busy_wait(30)` 后，最终达到 695 Hz。

### UF2 刷写现象说明

UF2 复制完成后 bootloader 会立即重启，虚拟 U 盘随之消失。Windows 有时会因为目标盘在文件复制确认前消失而提示“无法复制”，但固件实际上已经写入；有时文件系统确认先完成，则不会出现该提示。两种表现都可能是正常刷写。

判断刷写是否成功，应以 bootloader 盘自动消失、COM12 重新出现、上位机恢复接收以及新固件行为生效为准，不应以 Windows 是否弹出“无法复制”作为判断标准。

### 当前结论

- 当前扫描率：**695 Hz**。
- 当前完整扫描周期：约 **1.44 ms**。
- 24 通道一次完整扫描只进行 8 次三通道 SAADC 批量转换。
- USB CDC 的 62-byte 数据帧在当前速率下约产生 `695 × 62 ≈ 43.1 kB/s`，仍远低于 USB Full-Speed CDC 的可用带宽，因此 USB 不是当前瓶颈。
- 30 µs稳定时间目前表现稳定，但还需要用静止噪声和跨通道串扰测试确认模拟精度。
- 当前固件继续禁止所有 HID 输出，仅作为 24 通道霍尔采集设备运行。

## 2026-07-20：冲击 1000 Hz，第一阶段

### 目标与时间预算

上一版本实测为 695 Hz，即完整 24 通道扫描周期约 1.44 ms。1000 Hz 要求周期不超过 1.00 ms，因此需要再减少约 0.44 ms，等价于把周期缩短约 30.5%。第一阶段先采用不绕过 Zephyr ADC API 的低风险优化，并增加设备端微秒级性能测量。

### 已完成修改

1. **协议时间戳升级到微秒**：二进制协议升级为 v2，原 32-bit 时间字段由毫秒改为微秒。上位机同时兼容 v1 和 v2，并用微秒数据计算周期与抖动。计时源启用 Cortex-M4 DWT 周期计数器，而不是使用 32768 Hz 的内核系统计数器，以保证 5～20 µs阶段耗时具有足够分辨率。
2. **增加设备端分段计时**：每 256 次扫描发送一次 performance frame，记录 `scan_us`（扫描主体总耗时）、`address_us`（地址切换与 settle）、`adc_us`（八次三通道 ADC 批量读取）和 `process_us`（电压换算、状态判断及矩阵处理）。
3. **SAADC acquisition time**：三个 ADC 通道均由默认 10 µs改为 5 µs，保持 12-bit，未启用 oversampling。理论上每帧 24 个样本可减少约 120 µs acquisition time。
4. **4051 settle time**：由 30 µs改为 20 µs，继续使用 `k_busy_wait()`。八个地址理论减少约 80 µs。
5. **格雷码扫描**：地址顺序改为 `0 → 1 → 3 → 2 → 6 → 7 → 5 → 4`。相邻地址只改变一个地址 GPIO，稳态运行时 GPIO API 调用由每帧 24 次降到约 8 次；采样仍按照真实 Y 编号写回，串口通道顺序不变。
6. 上位机状态栏增加 `PERF scan = address + ADC + process` 实时显示，baseline JSON 同时输出这四个字段。

### 编译结果

- 构建成功，无新增编译错误。
- 最终设备树确认 `settle-time-us = 0x14`，即 20 µs。
- 三个 ADC 通道的 acquisition time 均为 `0x4005`，即 5 µs。
- 启用 DWT 精确计时后的最终 UF2 大小：135168 bytes。
- 固件位置：`app/build-megknob/zephyr/zmk.uf2`。

## 2026-07-20：第一阶段实测与上位机性能修复

第一阶段固件刷入后，完整 24 通道 scan rate 由约 695 Hz 提升到约 **800 Hz**。说明 5 µs acquisition、20 µs settle 和格雷码地址切换均已生效，但尚未达到 1000 Hz。

### 发现的问题

1. 上位机运行一段时间后，scan rate 数值没有明显变化，但波形逐渐变稀疏；点击“清屏”后暂时恢复。
2. ALL 24 CH 模式下 GUI 负载较高，会丢弃部分等待绘制的数据。
3. 原 `DISPLAY LAG` 使用“主机时间减设备时间”的历史最小偏移估算。主机和 MCU 没有进行时钟同步，两颗时钟还会产生漂移，因此该数值会把时钟漂移、串口批量到达和 GUI 积压混在一起，并不可靠。

### 根因

第一版 v2 微秒时间戳直接把 64 MHz DWT 的 32-bit 计数值换算成微秒，因此约每 `2^32 / 64 MHz = 67.1 s` 回绕一次。上位机只按照标准 32-bit 微秒字段约 71.6 分钟的回绕方式处理，导致设备时间在约 67 秒后倒退。历史窗口剪裁和横坐标因此异常；“清屏”只是清掉了跨越回绕点的数据，所以看起来能够重置。

此外，上位机原来无论当前时基是多少，都保存至少 20 秒原始数据。800 Hz 时约为 16000 帧，每 40 ms刷新都将整个 deque 转成列表、重新筛选、构造 NumPy 数组，并更新 24 个曲线及 24 个文本标签，运行时间越长负担越重。

### 修复内容

1. 固件用相邻 DWT 读数的差值累计为 64-bit 内部周期，再转换为 32-bit 微秒协议时间。DWT 自身每 67.1 秒回绕不再导致协议时间倒退；协议字段只在约 71.6 分钟按预期回绕。
2. 上位机增加时间戳展开，并兼容存在 67.1 秒回绕问题的第一版 v2 固件。
3. 历史缓冲只保留当前可见时基的约 110%，不再固定保存至少 20 秒。
4. 在转换 NumPy 数组之前先将绘图数据限制在约 1000 点，并确保始终保留最新点。
5. 关闭全局抗锯齿，启用 pyqtgraph `clipToView` 和 peak downsampling，24 条曲线宽度略微减小。
6. 通道数值标签由每 40 ms更新改为每 200 ms更新；波形仍保持 25 FPS。
7. 串口线程为每批解码数据记录主机到达时间。`DISPLAY LAG` 现在表示“串口线程完成解码到 GUI 实际处理最新数据”的队列等待时间，不再使用未同步的 MCU/PC 绝对时钟差。
8. `FRAME LOSS` 改为 `LOSS DEV/UI`：左侧为协议序号检测到的设备/传输丢帧，右侧为 GUI 有界队列为了保持实时性主动丢弃的旧帧。

### 验证

- 上位机 Python 语法检查通过。
- PyQt5 离屏窗口与绘图组件启动测试通过。
- 修复时间戳累计后的固件编译成功。
- 新 UF2：`app/build-megknob/zephyr/zmk.uf2`，135168 bytes。

刷入后应至少连续运行 2 分钟，确认跨过原来的 67.1 秒回绕点后波形密度不再变化；ALL 24 CH 模式重点观察 `LOSS DEV/UI` 的右侧计数和新的 `DISPLAY LAG`。

## 2026-07-20：长时间运行后时基缩短

### 现象

长时间传输后，可见波形覆盖的时间范围明显缩短，甚至不足 100 ms；点击“清屏”后恢复。

### 根因

新版协议使用 32-bit 微秒时间戳，约每 `2^32 µs = 71.6 min` 正常回绕一次。上位机为了兼容第一版 v2 固件，还保留了“约 67.1 秒 DWT 回绕”的识别分支，但旧版兼容判断位于标准 uint32 回绕判断之前。

当新版时间戳从接近 `0xffffffff` 回到 0 时，它同时满足“旧版时间戳大于 60 秒且新值接近 0”的条件。上位机因此只增加 `67,108,864 µs`，没有增加正确的 `4,294,967,296 µs`，展开后的设备时间倒退约 70 分钟。历史缓冲中随即残留相对于新时间的“未来样本”，造成横坐标和窗口剪裁异常。清屏会删除这些污染样本，所以能够暂时恢复。

### 修复

1. 首先检查向后跳变量是否大于 `0x80000000`；满足时一律按标准 uint32 回绕增加 `2^32`。
2. 只有不满足标准回绕、向后跳变在约 50～67 秒范围内时，才进入旧版 67.1 秒 DWT 兼容分支。
3. 旧版兼容分支允许回绕后的首帧在 0～10 秒内，避免短暂 GUI 停顿导致漏判。

该问题只存在于上位机时间戳展开逻辑，不需要再次刷写键盘固件；重启更新后的上位机即可。

## 2026-07-20：停止兼容 v2，升级协议 v3

旧版和新版固件曾共同使用协议 v2，但时间戳语义不同：第一版直接换算 32-bit、64 MHz DWT 值，约每 67.1 秒回绕；修复版发送 32-bit 微秒累计值，约每 71.6 分钟回绕。上位机只能根据跳变幅度猜测固件类型，兼容逻辑存在误判风险。因此决定停止兼容 v1/v2，固件和上位机统一只使用协议 v3。

### v3 时间处理

1. 固件每次生成数据帧时，只换算相邻两个 DWT 读数之间的短周期差值。
2. 短差值先转换为纳秒，再累加进 64-bit `timestamp_ns`，避免长期运行后对巨大周期累计值执行乘法换算造成溢出。
3. 协议仍发送 `timestamp_ns / 1000` 的低 32 bit，因此线上的微秒字段约每 71.6 分钟自然回绕。这是固定且唯一的 v3 语义。
4. 上位机发现时间戳向后跨越超过半个 32-bit 范围时，精确增加 `2^32 µs`。Python 整数没有 32/64-bit 固定宽度限制，展开后的时间轴可长期保持单调。
5. 删除旧版 67.1 秒 DWT 回绕的启发式兼容分支，上位机拒绝所有非 v3 数据帧，避免再次混淆协议语义。

升级后必须同时使用 v3 固件和新版上位机。旧 v1/v2 固件不会再显示数据。

## 2026-07-20：冲击 1000 Hz，第二阶段候选固件

第一阶段实测约 800 Hz，对应完整扫描周期约 1.25 ms。要达到 1000 Hz，需要进一步减少约 250 µs。第二阶段在保留 v3 时间协议、12-bit、无过采样、三通道 ADC 批量读取和格雷码扫描的基础上，继续压缩硬件等待与每帧软件固定开销。

### 修改内容

1. 三个 SAADC 通道的 acquisition time 由 5 µs降到 nRF52840 支持的最低档 3 µs。24 个样本理论减少约 48 µs。
2. 4051 settle time 由 20 µs降到 10 µs。八个地址理论减少约 80 µs。
3. 专用扫描工作队列不再在每帧结束后重新 `k_work_reschedule_for_queue()`。work handler 启动后直接连续扫描，消除每轮 delayable-work 重新入队和唤醒开销。
4. 连续扫描每完成一轮执行一次 `k_yield()`，让同优先级 CDC 发送线程获得运行机会，避免只提高内部扫描率却饿死串口输出。
5. CRC-16/CCITT-FALSE 从每字节 8 次逐 bit 运算改为 16 项 nibble 查表，每字节只进行两次查表更新。帧格式和 CRC 结果不变。
6. enable/disable 使用原子状态控制，防止重复启动扫描循环。

### 构建结果

- 固件编译成功。
- UF2：`app/build-megknob/zephyr/zmk.uf2`。
- UF2 大小：135680 bytes。
- 构建期间曾因第一次全量构建超时后遗留 Ninja 进程锁住依赖文件而失败；释放遗留进程后增量构建正常完成，不是代码编译错误。

### 刷入后验收

- 首先观察 scan rate 能否达到或超过 1000 Hz，并记录 `PERF scan/address/adc/process`。
- ALL 24 CH 连续运行，观察 `LOSS DEV/UI`；内部扫描超过 1000 Hz但 RX 低于 1000 fps 时，应优先优化 CDC 发送而不是继续降低模拟等待时间。
- 比较 800 Hz 版本与本版本的静止电压均值、峰峰噪声、完全按下幅值和相邻 Y 通道串扰。
- 3 µs acquisition 与 10 µs settle 均为激进配置。如果出现幅值系统性偏低、第一帧残留或噪声明显增加，应分别回退 acquisition 或 settle，而不是以错误采样换取频率数字。

### 第二阶段初次实测与传输瓶颈

第二阶段初次实测：scan rate 约 888 Hz，RX 约 862 fps，吞吐量约 53710 B/s，设备端 `PERF scan_us` 约 562 µs。

`1,000,000 / 562 ≈ 1779 Hz`，说明地址切换、settle、八次 ADC 批量采样和矩阵处理的扫描主体已经具备明显超过 1000 Hz 的能力。888/862 Hz 的限制主要位于 `PERF` 计时结束之后，即CRC、封包入队、线程调度和CDC发送，而不是4051或SAADC采样主体。因此暂不继续降低3 µs acquisition和10 µs settle。

本地驱动检查确认：

- Zephyr nRF SAADC 已通过 `nrf_saadc_buffer_init()` 使用 EasyDMA，每个4051地址的三个SAADC通道由DMA搬运到RAM；当前通用 `adc_read()` 仍会在每组采样时START、等待END并STOP。
- CDC ACM内部已有1024-byte TX ring buffer和USB bulk endpoint。
- 原发送线程却对每个62-byte帧调用62次 `uart_poll_out()`；862 fps时约为每秒53444次逐字节UART API调用。

### CDC批量发送优化

发送路径已改为Zephyr UART中断驱动模式：

1. 发送线程从消息队列取得一帧后，将完整62-byte帧放入共享TX frame并启用TX IRQ。
2. CDC ACM在TX ready回调中调用 `uart_fifo_fill()`，通常一次把完整帧放入其1024-byte ring buffer。
3. 如果ring buffer只能接受部分数据，保留offset并等待下一次TX ready继续，不截断帧。
4. 完整帧进入ring buffer后关闭TX IRQ并通过semaphore唤醒发送线程处理下一帧。
5. 不在普通线程中直接调用具有ISR语义的 `uart_fifo_fill()`，符合Zephyr UART中断API的调用模型。

这项修改保持v3帧格式、CRC、ADC配置和上位机协议不变，预期将每帧约62次CDC写调用降低为通常1次。固件编译成功，新UF2为 `app/build-megknob/zephyr/zmk.uf2`，大小136192 bytes。

刷入后应比较 scan rate、RX fps和 `LOSS DEV/UI`。如果RX接近或超过1000 fps，说明主要瓶颈已经解决；如果 `PERF` 仍为约562 µs而RX没有明显提升，则下一步检查USB workqueue调度及消息队列丢帧，而不是继续优化ADC。

### 1000 Hz 目标达成

CDC中断批量发送版本实测结果：

| 指标 | 实测值 |
|---|---:|
| Scan rate | **1216 Hz** |
| 平均完整周期 | **0.822 ms** |
| 周期抖动标准差 | **0.040 ms** |
| RX data frame rate | **1171 fps** |
| USB CDC吞吐量 | **72907 B/s** |
| 设备扫描主体 `PERF scan_us` | **610 µs** |

吞吐量换算为 `72907 / 62 ≈ 1175.9` 个总帧/秒。固件每256次扫描额外发送一个62-byte performance frame，扣除这部分后与上位机显示的1171个数据帧/秒基本一致，证明传输统计自洽。CDC从逐字节 `uart_poll_out()` 改为TX中断下整帧 `uart_fifo_fill()` 后，完整数据输出已经稳定跨过1000 fps，主要传输瓶颈得到解决。

Scan rate 1216 Hz 相比目标1000 Hz高约21.6%，周期0.822 ms比1.000 ms预算保留约178 µs余量。0.040 ms抖动约占平均周期4.9%，当前结果足以宣告1000 Hz目标达成。

`PERF` 从此前562 µs变为610 µs并不代表ADC硬件退化。批量CDC版本改变了扫描线程、USB workqueue和中断之间的CPU竞争关系；`PERF`测量覆盖扫描主体，期间可能被USB中断或更高优先级任务抢占，所以墙钟耗时会略有上升。即使按610 µs计算，扫描主体理论上限仍约为1639 Hz，当前无需继续绕过Zephyr `adc_read()`。

下一阶段不再追求更高空载频率，优先执行：

1. ALL 24 CH连续运行至少10分钟，记录 `LOSS DEV/UI`、CRC和display lag。
2. 检查3 µs acquisition与10 µs settle下的静止噪声、完全按下幅值和相邻Y通道串扰。
3. 比较800 Hz版本与1216 Hz版本的每通道均值、标准差和峰峰值，确认速度提升没有牺牲模拟精度。
4. 稳定性通过后，将目标运行频率考虑限制在1000 Hz，而不是持续无上限扫描，以换取约束明确的CPU余量和更稳定的USB调度。
